## 세션과 토큰

세션, 토큰의 차이점에 대해 정리해보았습니다.

### 1. 사이즈
- `세션` : 세션 ID만 실어 보내면 되므로 **트래픽을 적게 사용**함.
- `토큰` : 사용자 인증 정보와 토큰의 발급시각, 만료시각, 토큰의 ID등 담겨있는 정보가 세션 ID에 비해 방대하므로 세션 방식보다 **훨씬 더 많은 네트워크 트래픽을 사용**함.

 => JWT에 단순히 iss, sub, nbf, exp,iat, jti, typ 클레임만 실었는데 304 바이트가 다왔다고 함. 그에 비해 세션 ID는 단 6바이트. 50배가 넘는 트래픽 비효율임.

### 2. 안정성과 보안
- `세션` : 모든 인증 정보를 서버에서 관리하기 때문에 **보안 측면에서 유리**함.
    - 해커가 세션 ID를 탈취한다고 해도, 서버측에서 해당 세션을 무효 처리하면 됨.
    - 모든 데이터가 서버에 저장되기 대문에 아무나 열람할 수 없어 저장할 수 있는 데이터에 제한이 없음.
- `토큰`
  1. 서버가 트래킹하지 않고, 클라이언트가 모든 인증정보를 가지고 있기 대문에 토큰이 한번 해커에게 탈취되면 해당 토큰이 만료되기 전까지 피해를 볼 수 밖에 없음.
  2. 토큰에 실린 Payload가 별도로 암호화 되어있지 않으므로, 민감한 데이터는 실을 수없다. 즉, **Payload에 실을 수 있는 데이터가 제한**됨.
 
### 3. 확장성
- `세션` : 한대가 아닌 여러대의 서버가 요청을 처리하는 수평 확장을 사용하는데, 이때 별도의 작업을 해주지 않는다면 **세션 기반 인증방식은 세션 불일치 문제**를 겪게됨. 이를 해결하기 위해서 Sticky Session, Session Clustering 등의 추가작업을 해주어야함.
- `토큰` : 서버가 직접 인증 방식을 저장하지 않고, 클라이언트가 저장하는 방식을 취하기 때문에 **세션 불일치 문제로부터 자유로워 높은 확장성**을 가짐.

### 4. 서버의 부담
- `세션` : 서비스가 세션 데이터를 직접 저장하고 관리하기 때문에 **세션 데이터의 양이 많아지면 많아질수록 서버의 부담이 증가**함. 
- `토큰` : 클라이언트가 인증 데이터를 직접 가지고 있기 때문에, **유저의 수가 얼마나 되던 서버에 부담이 가지 않는**다.
  => **서버의 부담 측면**에서는 **토큰 기반 인증 방식이 더 유리**함.
